# Visual prototype

Use one or several visual alternatives only as needed to answer the question.
Reuse domain vocabulary, representative synthetic content, and the project's
visual conventions. A static sketch may suffice. If interaction matters, use an
isolated mock or disposable worktree; existing app context can help, but do not
modify production routes or wire real mutations under planning authorization.

When alternatives are useful, make the differences meaningful (information order,
layout, action flow). Provide a simple way to compare them; a URL variant switcher
is an option, not a mandatory architecture. Keep implementation effort proportional
to the uncertainty. Record the user's verdict and capture all relevant alternatives
as evidence following [the prototype skill](SKILL.md). Choosing a design does not
authorize promoting prototype code into the application.
